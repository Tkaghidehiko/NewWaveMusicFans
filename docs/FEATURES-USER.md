# ユーザー機能 仕様（ドラフト）

> ユーザー登録・アーティストブック・マヤ暦相性診断の設計メモ。
> **ブラッシュアップ前提のドラフト**。決まったものから確定させていく。

作成日: 2026-08-04 / 更新: 2026-08-04 / ステータス: 検討中

---

## 1. 概要

読者が「自分のアーティストを持ち、好きな記事を貯めていける」体験を提供する。
単なる読み物サイトから、**再訪する理由のあるサービス**へ。

### コア体験
```
マヤ暦診断でアーティストと出会う → ファンになる → 記事にいいね
→ アーティストブックに蓄積 → 推し遍歴が年表として残っていく
```

## 2. 機能一覧

### 2.1 ユーザー登録・ログイン
- **方式**: Supabase Auth を利用（自前実装はしない = セキュリティリスク回避）
- **ログイン手段**（候補）: Google / X(Twitter) / メール+パスワード
- **プロフィール**: 表示名、アバター（任意）、**生年月日**、マヤ暦KIN

### 登録時に生年月日を入力する（確定）
将来的に他の命式占い（四柱推命・算命学・西洋占星術など）と複合的に見られるようにするため、
KINの算出結果だけでなく **生年月日そのものを保存する**。

| 項目 | 必須 | 用途 |
|---|---|---|
| 生年月日 | 必須 | KIN算出。他の命式占いへの拡張の土台 |
| 出生時刻 | 任意 | 四柱推命の時柱、西洋占星術のハウス計算に必要 |
| 出生地 | 任意 | 西洋占星術のホロスコープ作成に必要 |

> **出生時刻と出生地も任意項目として最初から用意することを推奨。**
> 後から追加すると、既存ユーザー全員に再入力を依頼することになる。
> 任意なので入力しなくても登録は完了でき、入力したユーザーだけが将来の機能を使える。

#### 取り扱い上の注意
生年月日は個人情報にあたるため、以下を守る。
- プライバシーポリシーに取得項目と利用目的を明記する
- 生年月日そのものは他ユーザーに公開しない（公開するのはKINや紋章などの診断結果のみ）
- 退会時は確実に削除する

### 2.2 ファン登録と「推し期間」の記録 ★重要
通常の「お気に入り」ではなく、**期間を持つ記録**として設計する。

- ファンになった日 / やめた日を保持する
- ファンをやめても記録は残り、ブックに「推していた期間」として表示される
- 同じアーティストを再びファン登録した場合は、**新しい期間**として追加される
  （＝「1度目: 2026年3月〜8月」「2度目: 2027年1月〜」のように複数期間を持てる）

#### 2つの「消し方」を分ける（誤操作対策）
| 操作 | 挙動 | 置き場所 |
|---|---|---|
| **ファンをやめる** | 期間が終了。記録はブックに残る | アーティストページ（押しやすい場所） |
| **記録を削除する** | 期間そのものを消す。ブックからも消える | 履歴の詳細・設定内（意図的に押す場所） |

> UI方針: 日常操作である「やめる」は手軽に、取り消しのきかない「記録を削除」は一段深い階層に置き、確認ダイアログを挟む。

### 2.3 いいね → アーティストブック
- 記事に「いいね」ボタン
- いいねした記事は **記事に紐づくアーティストごとに自動で整理** される
- ⚠️ **前提**: 記事に「登場アーティスト」のタグ付けが必須。この紐付けがブックの土台。

### 2.4 アーティストブック（「本」のメタファーを活かす）
ブックは「今好きなものの一覧」ではなく、**読み返せる自分の記録**として作る。

- **表紙 / 目次** — 登録アーティスト数、総推し期間、いいね記事数
- **見開きページ** — アーティスト1組につき1ページ
  - アーティスト情報
  - **推し期間の年表**（現在進行中／過去の期間を帯で表示）
  - いいねした記事の一覧
  - マヤ暦の相性結果
- **栞（しおり）** — 後で読む記事
- **年表ビュー** — 全アーティストの推し遍歴を時系列で俯瞰する

> 期間を残す設計により、ブックは「今の推し」ではなく **「音楽遍歴の記録」** になる。
> 数年後に読み返す価値が生まれ、これは他サービスにない差別化になる。

### 2.5 マヤ暦ツォルキン相性診断
- **入力**: 生年月日 → **KIN番号（1〜260）** を算出
- **構成**: 20の太陽の紋章 × 13の銀河の音 = 260通り
- **アーティストとの相性**: アーティスト（またはメンバー個人）のKINと照合

#### メンバー一人ひとりとの相関を出す
バンド・グループの場合、**メンバー全員との相性を個別に表示**する。

```
あなた（KIN xx）
 ├─ Vo. Aさん …… 神秘の関係
 ├─ Gt. Bさん …… 類似の関係
 ├─ Ba. Cさん …… （関係なし）
 └─ Dr. Dさん …… 反対の関係
```

- 関係の種類（マヤ暦で一般に用いられるもの）:
  **神秘の関係 / 類似の関係 / 反対の関係 / ガイドの関係 / 同じ紋章**
- ⚠️ **判定ルールは実装前に出典を確定させる**（紋章・音の組み合わせ条件）。
  ここを誤ると診断結果そのものが破綻するため、計算ロジックはテストを書いて固める。
- KIN算出は**計算式・対応表で完結する**（外部API不要・即時・無料）

#### 実務上の課題
- **メンバーの生年月日が公開されていないケースが多い**
  → 対応: 判明しているメンバーのみ表示し、不明な場合は「非公開」と明示する
- **表記**: エンターテインメントとして提供する旨を明記する
- 補足: 日本で普及しているマヤ暦占いは、古代マヤ暦を元にした現代の体系（ドリームスペル）に基づく

### 2.6 レコメンド機能
KINと、これまでの好みの傾向をもとに、まだ知らないアーティストを提案する。
このサイトの目的である「次世代アーティストとの出会い」に直結する機能。

#### 判断に使う材料
| 材料 | 内容 |
|---|---|
| **マヤ暦の相性** | ユーザーのKIN × アーティスト（メンバー）のKIN |
| **好みの傾向** | いいねした記事のカテゴリ・ジャンル・国の偏り |
| **推し遍歴** | ファン登録したアーティストの傾向、推し期間の長さ |

#### 設置場所（複数箇所に分散させる）
| 場所 | 見せ方 |
|---|---|
| **トップページ** | ログイン時のみ「あなたへのおすすめ」枠を差し込む |
| **アーティストページ** | 「このアーティストを好きな人が注目している」 |
| **記事の末尾** | 「この記事を気に入ったなら」 |
| **診断結果ページ** | 相性の良いアーティストを提示し、そのままファン登録へ |
| **専用ページ `/discover`** | じっくり探したい人向けの一覧 |

#### 設計上の注意
- **登録直後は好みのデータがない**（コールドスタート）。
  → 最初はKINの相性のみでレコメンドし、いいねが貯まるにつれて好みの比重を上げる
- **偏りすぎない**ようにする。似たものばかりでは「次世代との出会い」にならないため、
  意図的に傾向から外れたアーティストを一定割合で混ぜる
- 精度は運用しながら改善する。どのレコメンド経由でファン登録されたかを計測できるようにしておく

## 3. データ構造（案）

| テーブル | 主な内容 |
|---|---|
| `profiles` | ユーザー情報（Supabase Auth と紐付け）、`birthdate`、`birth_time`、`birth_place`、`kin` |
| `artists` | アーティスト情報（名前、国、ジャンル、外部ID） |
| `artist_members` | メンバー個人（名前、パート、`birthdate`、`kin`） |
| `articles` | 記事（タイトル、本文、カテゴリ、出典） |
| `article_artists` | **記事 ⇄ アーティストの紐付け（多対多）** ← ブックの要 |
| `fan_periods` | **推し期間**（下記参照） ← ブックの要 |
| `article_likes` | ユーザー ⇄ いいねした記事 |

### `fan_periods` の設計
```
id
user_id
artist_id
started_at     ファンになった日時
ended_at       やめた日時（NULL = 現在も継続中）
deleted_at     記録削除の日時（NULL = 有効）※誤操作対応
```

- **現在のお気に入り** = `ended_at IS NULL AND deleted_at IS NULL`
- **推し遍歴** = そのユーザーの全レコード（`deleted_at IS NULL`）
- 再登録は新規レコードとして追加（同一アーティストに複数期間を許容）

> アーティストブックは新規テーブルではなく、上記を組み合わせた**ビュー**として実現できる。

### プライバシー配慮の設計
- **生年月日は保存する**（他の命式占いへ拡張するため。2.1 参照）
  そのぶん、公開範囲・保存期間・削除導線を明確にして扱う
- 他ユーザーに見せるのは診断結果（KIN・紋章など）のみ。生年月日そのものは公開しない
- メンバーの生年月日は**公表されている情報のみ**を扱う

## 4. 追加されるページ

```
/login  /signup                認証
/mypage                        マイページ（プロフィール・設定）
/mypage/book                   アーティストブック（表紙・目次）
/mypage/book/[artist]          アーティスト別ページ（推し期間の年表）
/mypage/history                推し遍歴の年表ビュー・記録の管理／削除
/artists/[slug]                アーティストページ（ファンになるボタン）
/fortune                       マヤ暦診断
/fortune/result/[id]           診断結果（シェア用）
/discover                      レコメンド（KIN × 好みの傾向）
/privacy  /terms                プライバシーポリシー・利用規約
```

## 5. ⚠️ 法的・運用上の注意（重要）

ユーザー登録を入れると **個人情報を預かる** ことになる。以下が必須。

- **プライバシーポリシーの掲載**（個人情報保護法。取得する情報・利用目的・問い合わせ先を明記）
- **利用規約の掲載**
- **退会・データ削除の導線** — ユーザーが自分のデータを完全に消せること
  → 「記録を削除」機能はこの要請とも合致する。**退会時は物理削除**とする
- パスワードは自前で持たない（Supabase Auth に任せる）

## 6. 段階的な進め方（推奨）

**記事がないとブックもいいねも機能しない**ため、コンテンツが先。

| 段階 | 内容 | 理由 |
|---|---|---|
| **Step 1** | 記事サイトのMVP | まず読むものを作る |
| **Step 2** | 公開・記事を貯める | いいねする対象が必要 |
| **Step 3** | アーティストページ + 記事へのアーティストタグ付け | ブックの土台 |
| **Step 4** | ユーザー登録 + ファン登録（`fan_periods`） | 法務ページも同時に |
| **Step 5** | いいね + アーティストブック | コア体験の完成 |
| **Step 6** | マヤ暦診断 | 集客の入口として |
| **Step 7** | レコメンド | いいねが貯まって初めて精度が出る |

> **Step 3〜4 のデータ構造は Step 1 の時点で見据えて設計する**。後付けは作り直しになる。
> 特に `fan_periods` は「期間を持つ」前提で最初から作ること（単純なお気に入りテーブルから後で移行すると、過去の履歴は復元できない）。
