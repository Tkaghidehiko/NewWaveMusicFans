# ユーザー機能 仕様（ドラフト）

> ユーザー登録・アーティストブック・占いレコメンドの設計メモ。
> **これはブラッシュアップ前提のドラフト**。決まったものから確定させていく。

作成日: 2026-08-04 / ステータス: 検討中

---

## 1. 概要

読者が「自分のアーティストを持ち、好きな記事を貯めていける」体験を提供する。
単なる読み物サイトから、**再訪する理由のあるサービス**へ。

### コア体験
```
アーティストのファンになる → そのアーティストの記事が届く
→ 気に入った記事にいいね → 自分のアーティストブックに蓄積される
```

## 2. 機能一覧

### 2.1 ユーザー登録・ログイン
- **方式**: Supabase Auth を利用（自前実装はしない = セキュリティリスク回避）
- **ログイン手段**（候補）:
  - メールアドレス + パスワード
  - Google ログイン（推奨・登録の心理的ハードルが低い）
  - X(Twitter) ログイン（音楽ファン層と相性が良い）
- **プロフィール**: 表示名、アバター（任意）

### 2.2 ファン登録（マイアーティスト）
- アーティストページから「ファンになる」で登録
- マイページで一覧・並び替え・解除ができる
- ファン登録したアーティストの新着記事が優先的に表示される

### 2.3 いいね → アーティストブック
- 記事に「いいね」ボタン
- いいねした記事は **記事に紐づくアーティストごとに自動で整理** される
- アーティストブック = 「自分がファンのアーティスト」×「そのアーティストのいいね記事」のコレクション
- ⚠️ **前提**: 記事に「登場アーティスト」のタグ付けが必須。この紐付けがブックの土台。

### 2.4 占いレコメンド
- 目的: 新しいアーティストとの出会いを作る。**SNSでシェアされやすい入口コンテンツ**にもなる
- 方式（候補）:
  - **A. 質問式診断** — 数問answering → タイプ判定 → おすすめアーティスト（再現性があり調整しやすい）
  - **B. 生年月日・星座ベース** — 占い感が強い。ただし当たり外れの体感に依存
  - **C. AI診断** — 自由記述からAIがレコメンド（体験は面白いがコストがかかる）
- 結果から直接「ファンになる」に繋げる導線を置く
- **表記上の注意**: エンターテインメントである旨を明記する

## 3. データ構造（案）

| テーブル | 主な内容 |
|---|---|
| `profiles` | ユーザー情報（Supabase Auth と紐付け） |
| `artists` | アーティスト情報（名前、国、ジャンル、外部ID など） |
| `articles` | 記事（タイトル、本文、カテゴリ、出典） |
| `article_artists` | **記事 ⇄ アーティストの紐付け（多対多）** ← ブックの要 |
| `user_favorite_artists` | ユーザー ⇄ ファン登録（多対多） |
| `article_likes` | ユーザー ⇄ いいねした記事（多対多） |
| `fortune_results` | 占い結果の履歴（任意） |

> アーティストブックは新規テーブルではなく、上記を組み合わせた**ビュー**として実現できる。

## 4. 追加されるページ

```
/login  /signup                認証
/mypage                        マイページ（プロフィール・設定）
/mypage/book                   アーティストブック
/mypage/artists                マイアーティスト一覧
/artists/[slug]                アーティストページ（ファンになるボタン）
/fortune                       占い
/fortune/result/[id]           占い結果（シェア用）
/privacy  /terms                プライバシーポリシー・利用規約
```

## 5. ⚠️ 法的・運用上の注意（重要）

ユーザー登録を入れると **個人情報を預かる** ことになる。以下が必須になる。

- **プライバシーポリシーの掲載**（個人情報保護法。取得する情報・利用目的・問い合わせ先を明記）
- **利用規約の掲載**
- **退会・データ削除の導線**（ユーザーが自分のデータを消せること）
- パスワードは自前で持たない（Supabase Auth に任せる = 漏洩リスクの最小化）

> これらは「後で」ではなく、**ユーザー登録機能を公開する時点で同時に必要**。

## 6. 段階的な進め方（推奨）

いきなり全部は作らない。**記事がないとブックもいいねも機能しない**ため、コンテンツが先。

| 段階 | 内容 | 理由 |
|---|---|---|
| **Step 1** | 記事サイトのMVP（現行計画通り） | まず読むものを作る |
| **Step 2** | 公開・記事を貯める | いいねする対象が必要 |
| **Step 3** | アーティストページ + 記事へのアーティストタグ付け | ブックの土台 |
| **Step 4** | ユーザー登録 + ファン登録 | ここで法務ページも同時に |
| **Step 5** | いいね + アーティストブック | コア体験の完成 |
| **Step 6** | 占いレコメンド | 集客の入口として |

> ただし **Step 3 のデータ構造だけは Step 1 の時点で見据えて設計する**。後付けは全記事の作り直しになる。

## 7. これから決めること

1. ログイン方法（Google のみ？ メール併用？）
2. 占いの方式（質問式 / 生年月日 / AI）
3. アーティストブックの見せ方（本棚風？ リスト？ カード？）
4. いいね以外の反応（「後で読む」「聴いた」など段階を作るか）
5. 他ユーザーのブックを見られるようにするか（公開/非公開）
